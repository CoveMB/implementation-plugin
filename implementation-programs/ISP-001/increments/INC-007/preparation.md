## Design options and decision

### Recommended: one focused continuity/closure controller with exact state bindings

Add `continuity_closure.py` and `continuity-closure.md`. Use versioned frozen records, pure deterministic validators and Markdown renderers for lean briefs, handoffs, conversation assessments, resume context, closure reconciliation, closure packets, and later-action decisions. Add a read-only `validate-bundle` command for exact JSON/Markdown equality and a bounded rollover operation that composes accepted state-authority persistence while reporting per-file receipts and partial-progress recovery.

Keep semantic continuity policy in the new reference and make the front door route there. Reuse accepted source/program/state/preparation/execution/review owners. Add only a narrow state-authority closure binding so `active -> awaiting-closure-approval` requires validated reconciliation and an exact packet, and `awaiting-closure-approval -> closed` requires an explicit approval bound to that packet. Later action decisions require the closed state, bound closure approval, and a separate exact action authorization.

### Rejected: extend state authority with the full continuity and closure workflow

State authority owns low-level lifecycle, approval, authorization, and persistence invariants. Brief content, handoff semantics, conversation suitability, program-wide requirement reconciliation, and human closure packets are higher-level workflow evidence. Combining them would enlarge an already substantial module and couple state transitions to Markdown generation and traceability semantics.

### Rejected: separate prompt, handoff, resume, reconciliation, closure, and later-action modules

These responsibilities share one exact program/revision/workspace/status/artifact binding graph and one ordering invariant. Six modules would duplicate schema loading, digest checks, error ordering, fixtures, and CLI surfaces without independent consumers. A later demonstrated size or reuse pressure can justify a bounded split.

### Rejected: prose-only handoffs and closure checks

Prose presence cannot prove required brief fields without policy duplication, current workspace/head equality, full-mode renewal, complete requirement disposition, accepted packet integrity, closure approval binding, or later-action separation. Deterministic semantic records are warranted, while the generated Markdown remains the human navigation surface.

## Risks and mandatory stops

- **Policy duplication:** generated briefs or handoffs may grow into a competing workflow. Enforce exact semantic fields, explicit omitted-policy detection, deterministic renderers, and representative concision tests rather than a raw character threshold alone.
- **Stale navigation authority:** a matching-looking handoff could conceal moved head, workspace, program revision, or artifact bytes. Require independent repository observation and exact persisted digest bindings; never let handoff prose supply authority.
- **Boolean conversation quality:** one caller-selected flag could make `approval:full` continuation performative. Require evidence for every suitability predicate, explicit mandatory-stop reasons, and renewed user authority in a new conversation.
- **Premature INC-008 start:** generating the valid next brief is an INC-007 integration checkpoint, not implementation authority. Do not change the current increment identity or run INC-008 work under INC-007 authorization.
- **Premature ISP-001 reconciliation:** closure validators are exercised only with neutral fixtures in INC-007. Actual ISP-001 reconciliation begins only after accepted INC-008 and separate closure authority.
- **State bypass:** direct lifecycle mutation could enter closure states without semantic evidence. Add a narrow exact reconciliation/packet binding to state authority and negative tests for bypass attempts.
- **Inferred later action:** closure approval may be mistaken for draft-PR, merge, release, deployment, migration, or provider authority. Require both a closed program with exact closure approval and a separately bound action authorization; never perform the action in validators.
- **Schema/state growth:** one record per semantic invariant is enough. Do not persist conversation transcripts, duplicated policy, speculative future decisions, secrets, or redundant state.
- **Partial multi-file writes:** cross-increment rollover and closure artifacts cannot be made transactionally atomic across all files. Use accepted per-file compare-and-swap/append-only primitives, deterministic write order, receipts, inert partial-record handling, and fresh resume validation; do not claim hostile-concurrency safety.
- **Program amendment:** stop if implementation changes requirements, acceptance, scope, public behavior, protected contracts, security/privacy obligations, risk posture, data ownership, dependencies, sequencing, or user review cadence.
- **Authority:** stop on any changed accepted byte, branch/head/base/workspace mismatch, active Git operation, conflict, missing exact plan approval, missing action grant, requested staging/commit, INC-008 execution, actual ISP-001 closure reconciliation, or consequential external action.
